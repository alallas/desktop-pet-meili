## 1. Rust 工具链与链接

### 坑 1：每个新 shell 里 cargo 不在 PATH
- 现象：`cargo: command not found`（cargo 装在 `$HOME/.cargo/bin`，Git Bash 不自动加载）。
- 解法：`source scripts/dev-shell.sh`，或手动 `export PATH="$HOME/.cargo/bin:$PATH"`。

### 坑 2：MSVC 走不通（本机无 Windows SDK）
- 现象：MSVC 工具链存在，但全盘找不到 `kernel32.lib`（没装 Windows SDK），链接必失败。
- 解法：固定走 `stable-x86_64-pc-windows-gnu` 路线，不要试图修 MSVC。

### 坑 3：windows-gnu 默认链接产出"Windows 拒绝加载"的 PE
- 现象：编译"成功"，但运行报"指定的可执行文件不是此操作系统平台的有效应用程序"；Git Bash 下则报 `Exec format error`。`file` 看 PE 头完全正常。
- 根因：本机可用的 mingw binutils 是 2015 年的 ld 2.25.1，与新版 rust 的导入库/目标文件混链，产出结构损坏的 PE（链接时就有 `corrupt .drectve` 警告）。
- 解法（已固化）：仓库根 `.cargo/config.toml` 强制走 rust 自带 rust-lld：
  ```toml
  [build]
  rustflags = ["-Zunstable-options", "-Clinker-flavor=gnu-lld", "-Clinker=rust-lld", "-Clink-self-contained=y"]
  [env]
  RUSTC_BOOTSTRAP = "1"   # stable 上用 -Z 需要
  ```
  验证命令：`RUSTC_BOOTSTRAP=1 rustc -Zunstable-options -C linker-flavor=gnu-lld -C linker=rust-lld -C link-self-contained=y main.rs`

### 坑 4：rustup 自带的 self-contained dlltool.exe 不能用
- 现象：`CreateProcess` 失败——它内部调 `as.exe`，但 self-contained 目录里没有。
- 解法：用 `tools/m2w64`（anaconda 的 m2w64-binutils）里的 binutils，把它排在 PATH 前面；不要用 rustup 那份。

### 坑 5：ld 找不到导入库时，LIBRARY_PATH 不顶用
- 现象：`-lmsvcrt -luser32 -lkernel32` 等找不到；设了 `LIBRARY_PATH` 也没用（链接实际经 gcc 驱动转发，行为不符合预期）。
- 解法：不要折腾环境变量，直接按坑 3 切 rust-lld 根治。

### 坑 6：Git Bash 的 `/usr/bin/link.exe` 会遮蔽 MSVC 的 link
- 解法：GNU 路线下与此无关；若未来修 MSVC，先处理 PATH 遮蔽。

## 2. 资源编译（windres）

### 坑 7：windres 预处理要调 gcc，缺了报 "preprocessing failed"
- 现象：build 脚本报 `windres failed to compile resource.rc (exit code: 1)`，手动跑 windres 看到 `'gcc' 不是内部或外部命令`。
- 根因：windres 用 `gcc -E` 做预处理；PATH 里只加了 binutils 目录、没加 gcc 目录。
- 解法：PATH 必须**同时**包含 `tools/m2w64/Library/mingw-w64/bin`（binutils，含 windres）和 `tools/m2w64-gcc/Library/mingw-w64/bin`（gcc）。`scripts/dev-shell.sh` 已配好。

## 3. 进程与窗口操作（Git Bash 环境）

### 坑 8：Git Bash 无法直接执行本工程编译的 exe
- 现象：`./chaojiandai.exe` 报 `Exec format error`，但 `file` 显示是合法 PE。
- 解法：用 `powershell -NoProfile -Command "Start-Process '...'"` 或 `cmd /c` 启动；不要用 `cmd //c start`（见坑 9）。

### 坑 8b：GDI 截屏（CopyFromScreen）会漏拍分层透明窗口，排查时极易误判为"窗口没渲染"
- 现象：桌宠在屏幕上明明可见，GDI 全屏截图里整个窗口消失；曾因此误判为 WebGL 合成失败，白查半天。
- 解法：截屏一律用 DXGI 方式——`scripts/screenshot_dxgi.py`（python + dxcam，截的是物理分辨率 2560x1600，比 GDI 的逻辑分辨率还清晰）。注意 GDI 截屏在开启远程控制/投屏类会话后更容易漏拍。

### 坑 8c：exe 运行中无法覆盖编译，报"拒绝访问 (os error 5)"
- 解法：每次 `cargo build` 前先 `powershell Stop-Process -Name chaojiandai -Force`。已列入标准构建流程。

### 坑 8d：PowerShell 5.1 按 GBK 读脚本，含中文注释的 .ps1 会直接解析失败
- 现象：`MissingEndCurlyBrace` 之类莫名报错。
- 解法：`scripts/*.ps1` 里只写 ASCII（注释也用英文）。

### 坑 9：`cmd //c start` 和 `tasklist //FI` 在 Git Bash 里会挂起
- 现象：命令不返回直到超时。
- 解法：一律改用 PowerShell——启动用 `Start-Process`，查进程用 `Get-Process`。

### 坑 10：cargo 有时不显示 build 脚本（build.rs）的 stderr
- 现象：`failed to run custom build command (exit code: 101)`，只有 stdout，panic 信息看不到；还会重放旧的缓存输出，极具迷惑性。
- 解法（定位法）：在 build.rs 里 `std::panic::catch_unwind(|| tauri_build::build())`，把 panic 信息写进文件再退出：
  ```rust
  let p = std::path::Path::new(&std::env::var("OUT_DIR").unwrap())
      .parent().unwrap().parent().unwrap().join("build-panic.txt");
  ```
  配合 `cargo clean -p <包名>`（别 clean 全部，重编译很慢）强制重跑。
- 补充：前端状态排查可让页面把状态 `invoke` 给 Rust 写日志文件（`debug_log` command，日志在 `%TEMP%\chaojiandai-debug.log`），比截图可靠。

### 坑 10b：排查"窗口内容不显示"类问题时，先怀疑截图工具，再怀疑渲染
- 教训：曾同时改两个变量（noRedirectionBitmap + disable-gpu-compositing）导致无法归因；且这两个标志在本机均为死路（WebGL 内容不进合成、FPS 掉到 23），**不要再用**。

## 7. Python 语音链路（M0-3）

### 坑 13：sherpa-onnx 2.0.1 的三个 API 坑
- `VadModelConfig(...).validate()` **返回 bool（True）**，不是 config——传给 `VoiceActivityDetector` 会报 `Invoked with: True`。直接传 config 对象即可。
- VAD 检出判断：`VoiceActivityDetector` 没有 `front()` 方法属性说法——`detector.empty()` 判空，`front`/`pop` 取段；`len(detector.front())` 会报 `SpeechSegment is not callable` 之类错误。还有 C++ 警告提示 front 只能在非空时调。
- KWS（KeywordSpotter）是**流式解码器**：stream 必须跨 chunk 复用，每帧新建 stream 喂 80ms 会永远检不出；检出后先 `get_result()` 存变量再 `reset_stream()`（取结果在 reset 之后调用会拿到空）。

### 坑 14：pip install 大 wheel 超时被杀 ≠ 下载失败
- 现象：`pip install torch` 跑满 300s 超时被杀，但缓存里 wheel 其实是完整的。
- 解法：看目标文件实际大小 vs HEAD 请求的 Content-Length，对上就 `pip install <本地whl>`；半截文件用 `curl -C -` 续传。
- 教训：下载慢的根源是单连接被限到 ~135–450KB/s，大文件留足预期。

### 坑 15：hf_hub_download 下大文件可能 0 字节挂起
- 现象：`hf_hub_download` 下载 327MB 的 pth，几分钟进度为 0（重定向后的 CDN 连接挂死），无报错无重试。
- 解法：**curl 分段并行**——HEAD 拿 Content-Length，按 8 段 `curl -r start-end`，每轮循环把各段 `.new` 追加合并，直到总长一致再 `cat` 合并。resolve URL 结构：`https://hf-mirror.com/<repo>/resolve/main/<file>`。
- 注意 hf-mirror API（`/api/models/...`）有共享 IP 限流（10000 次/5 分钟），报 429 时按 `retryAfter` 等待重试；`hf_hub_download` 前设 `HF_ENDPOINT=https://hf-mirror.com`。

### 坑 16：kokoro pip 包的中文-only 安装（本机已打补丁，重装 Python 需重做）
- 现象：`pip install kokoro misaki[zh]` 会拉 `misaki[en]` → **spacy 依赖地狱**（pip 在 spacy 4.0.0.dev3 等版本间疯狂回溯下载，永不收敛）。
- 解法（按序）：
  1. `pip install --no-deps kokoro misaki`（tuna 镜像）
  2. 手动补：`soundfile huggingface_hub loguru transformers attrs addict ordered_set num2words pypinyin jieba cn2an zhon`
  3. **打补丁**：`site-packages/kokoro/pipeline.py` 第 5 行 `from misaki import en, espeak` 是无条件顶层导入，纯中文（lang_code='z'）也强制要 spacy/espeak-ng。改成 `_LazyModule` 懒加载（en.MToken 注解缺失时降级为 list）。补丁内容见该文件顶部注释 `PATCH(chaojiandai)`。
- 模型加载（离线/加速）：
  - `KModel(config=hf_hub_download("hexgrad/Kokoro-82M","config.json"), model="models/kokoro-v1_0.pth")` 支持本地权重路径，**不必进 HF 缓存**。
  - 中文音色文件名是 `voices/zf_xiaobei/xiaoni/xiaoxiao/xiaoyi.pt`，**不是 zf_001 这类编号**（404 过的教训）。
  - 权重 `kokoro-v1_0.pth`（327,212,226 字节）下载放 `models/`（gitignored）；config.json 和 voices 在 HF 缓存 `C:\Users\79879\.cache\huggingface`。
- 选型记录：vits-melo-tts-zh_en（sherpa-onnx）已下载到 `models/tts-melo/` 但**实测 CPU RTF≈3.4（44.1kHz）太慢淘汰**；Kokoro-82M CPU RTF≈0.45 胜出。

### 坑 17：用户自己 shell 里的 `python` ≠ 装依赖的那个 Python
- 现象：在 PowerShell 里跑 `python scripts/voice_chain_demo.py` 报 `No module named 'numpy'`——依赖都装在 Kimi 托管环境 `D:\KimiData\daimon-share\daimon\runtime\python\.venv\Scripts\python.exe`，系统 python 是另一个。
- 解法：仓库根有 `run-voice.bat`，自动选带依赖的解释器（不存在才回退系统 python）。手动跑则用全路径调用托管 python。

### 坑 18：sherpa-onnx 原生层报错是"打印一行 + exit(127)"，无 Python 堆栈
- 现象：`python scripts/voice_chain_demo.py --tts`（麦克风模式）**零输出、3 秒后退出的、退出码 127**——不是启动慢，是 native 代码 `exit()` 了整个进程。
- 根因：本例是 `KeywordSpotter` 打开相对路径 `keywords.txt` 失败（实际在 `models/kws/`），`InitKeywords: Open keywords file failed` 打到 stdout 后 `exit(127)`。文件路径 bug 被静默掩盖。
- 解法：① 怀疑原生库静默退出时，先 `-u` 跑一遍看有没有那一行 native 报错；② 给 sherpa-onnx 传的路径**一律绝对路径**（`load_kws` 已把相对路径锚定到 `models/`）。

### 坑 19：silero VAD 的"说话中"判断要用 is_speech_detected()，不能看 empty()
- 现象：麦克风实测长句说到一半被截断（转写只剩残句）。
- 根因：silero 的语音段（segment）要等说话结束 + 静音窗口后才从队列吐出——**说话过程中 `detector.empty()` 恒为 True**，拿它当"沉默"会让 0.8s 静音阈值在说话中就被攒满。
- 解法：用 `detector.is_speech_detected()`（实时状态）控制静音计数；empty()/front()/pop() 只用来 drain 已完成的段。

### 坑 20：winsdk 的 SMTC 媒体状态枚举值
- `PlaybackStatus` 实际映射：`0=已关闭 1=已打开 2=切换中 3=已停止 4=播放中 5=已暂停`（官方文档顺序和直觉相反，4 才是播放中）。
- winsdk 的 WinRT API 全是 asyncio 风格：`GlobalSystemMediaTransportControlsSessionManager.request_async()` 要在 asyncio 里 await。
- **Chrome 视频标签页会注册为 SMTC 媒体会话**——浏览器里看什么视频走 SMTC 就能拿到标题/播放状态，不必先做浏览器扩展。

### 坑 21：transformers 5.x 的 VLM 加载与下载渠道
- `AutoModelForVision2Seq` 在 transformers 5.x **已移除**，用 `AutoModelForImageTextToText`（Idefics3/SmolVLM v1 映射在这里）。
- ModelScope 下载 URL 直接可用：`https://www.modelscope.cn/models/<org>/<repo>/resolve/master/<file>`，单连接约 1MB/s（比 hf-mirror 快一个量级），大文件 `curl -C -` 两轮即可。
- 实测结论：SmolVLM-256M 这类小 VLM 在纯 CPU 上**延迟与图片分辨率无关**（640x400 和 2560x1600 都是 ~28s，瓶颈在 LM 逐 token 解码）——降采样救不了本地 VLM 延迟。

### 坑 22：GitHub Releases CDN 是"抽风式"封锁 + 工具超时会留僵尸 curl
- 现象：`objects.githubusercontent.com` 间歇性封禁——有时能跑满，传 200-500MB 后又封几分钟，循环往复。大文件下载会反复"无法获取文件大小"。
- 解法：① 用 `scripts/parallel_dl.sh <URL> <输出> [段数]`（Range 分段并行 + 断点续传，反复执行同一命令即可，HEAD 拿不到大小时自动用 Range 探测）；② OllamaSetup 这种 1.8GB 的怪物放弃，改找 25MB 的 llama.cpp 官方 CPU zip（build b12283，含 llama-server）。
- **工具超时会杀掉 shell 但可能留下 curl 僵尸进程**，下一轮 `cat >>` 追加会把分段写重复（part 变成 2 倍大）→ 合并后 ZIP 损坏。每次重试前先 `Get-Process curl | Stop-Process -Force`，发现 part 超尺寸就丢弃重下。
- llama-cpp-python 在 PyPI/tuna **没有 Windows 预编译 wheel**（只有 sdist，需 MSVC 编译）——本机无 MSVC，别走这条路。

### 坑 23：Qwen3 是推理模型，语音对话必须关思考
- 现象：llama-server 流式返回里 `delta.content` 一直为 null，全在 `reasoning_content` 里——按 content 解析拿不到首 token。
- 解法：请求体加 `"chat_template_kwargs": {"enable_thinking": false}`（Qwen3 的 `/no_think` 开关）。实测关掉后首 token 0.33s，开着会先推理几十秒。
- Git Bash 里 curl `-d '中文'` 会把 UTF-8 转成 GBK 发出去（llama-server 报 ill-formed UTF-8）——带中文的 JSON 一律用 Python urllib 发，别用 curl。

### 坑 24：pyaudiowpatch 新版不再有 as_loopback 参数
- 0.2.12.x（PortAudio 上游合并 WASAPI loopback 后）：回环设备直接出现在设备列表（名字带 `[Loopback]` 后缀），`get_default_wasapi_loopback()` 拿到设备字典后**像普通输入设备一样 open** 即可，传 `as_loopback=True` 会报 TypeError。
- 旧教程/示例代码都是老 API，别照抄。

## 8. SQLite 落地（M1-1）

### 坑 25：本机没有任何能编译 sqlite3.c 的 C 编译器，rusqlite bundled 走不通，最终用官方预编译 dll + 导入库（一连串坑）

- **坑 25a：m2w64-gcc 5.3 的 stdarg.h 是 `#include_next` 转发壳，缺 mingw-w64 运行时头文件**。
  解法：tuna anaconda msys2 频道（tar.bz2 可直接解）下载 `m2w64-headers-git-5.0.0.4636.c0ad18a-2` → `tools/m2w64-headers/`、`m2w64-winpthreads-git-5.0.0.4634.697f757-2` → `tools/m2w64-winpthreads/`；`scripts/dev-shell.sh` 已配 `C_INCLUDE_PATH`。**注意：补上头文件后 gcc 5.3 编 sqlite3.c 仍然 ICE**（libbacktrace 崩溃退出），所以这只是必要不充分条件。
- **坑 25b：国内镜像没有 msys2 的 mingw64/ucrt64 仓库**（tuna/ustc/nju/tencent/huawei/aliyun/sjtu 全部 404），拿不到现代 mingw gcc；tuna 只有 `msys` 仓库（msys-2.0 运行时 gcc，产物 ABI 不通用）。**连带后果：凡依赖 C 库的 Rust 工具装不了**——`cargo install cargo-deny` 在 zstd-sys 上同样 ICE 崩盘（已实测）。许可证扫描用 `scripts/check-licenses.py`（解析 cargo metadata + node_modules，零编译）替代 cargo-deny，见工程规范 §6。M1-3 的 sherpa-onnx 若也需编译 C/C++，提前预案。
- **坑 25c（正解）：sqlite.org 官方预编译 `sqlite-dll-win-x64-<ver>.zip`（仅依赖 KERNEL32，CRT 静态链）**。
  - URL 年份目录是**发布年**（当前 `https://www.sqlite.org/2026/...`，从 download.html 现抓，别猜）；官网偶发 schannel 断连，重试即可。
  - 解压到 `tools/sqlite3/`（已 gitignore）：`dll/sqlite3.dll`+`dll/sqlite3.def`，头文件另下 `sqlite-amalgamation-<ver>.zip`。
  - `rusqlite default-features=false` + 显式 `libsqlite3-sys = { version = "0.30", default-features = false }`（其默认特性就是 bundled）；路径走仓库根 `.cargo/config.toml` 的 `[env] SQLITE3_LIB_DIR / SQLITE3_INCLUDE_DIR`（`relative = true`）。
  - **def 文件必须补 `LIBRARY sqlite3.dll` 行**（官方 def 没有）：否则 dlltool 生成导入库时 DLL 名是 null，rust-lld 会把导入表名字写成字面量 `"(null)"`，运行时 `STATUS_DLL_NOT_FOUND (0xc0000135)`——objdump 里表现为一个 `(null)` DLL Name，极具迷惑性。解法：`{ echo "LIBRARY sqlite3.dll"; cat sqlite3.def; } > fixed.def && dlltool -d fixed.def -l libsqlite3.a`。
  - **rust-lld 的 `-lsqlite3` 不会直接吃 `.dll`**（试过移走导入库→`unable to find library`），导入库是必需的。
- **坑 25d：`cargo test` 的测试二进制在 `target/<profile>/deps/` 下运行**，需要 `sqlite3.dll` 和 `WebView2Loader.dll`（tauri 只拷到 `target/<profile>/`）都在 deps/ 里——`src-tauri/build.rs` 已统一拷贝。改导入库等内容后 cargo 不重链，要 `cargo clean -p chaojiandai` 再测（允许范围内）。
- **坑 25e：`rusqlite::Connection` 是 Send 不是 Sync**，Tauri `app.manage()` 要求 Send+Sync → `Mutex<Connection>` 包装。
- **坑 25f：npm 直连 registry.npmjs.org 极慢，`npm i` 常跑满 300s 超时被杀**——但已下载的包会留在 cache，**反复重跑同一命令即可断点续装**（第三次通常收尾）；specta 系依赖只有 rc 版，`cargo add specta@2` 找不到，需手写 `"2.0.0-rc.28"` 进 Cargo.toml。tauri-specta 还需要显式开 `derive` 特性（默认全关）与 specta 的 `serde_json` 特性。
- 打包安装器时需把 `sqlite3.dll` 一并分发（tauri resources，M1-1 后半做）；dll 版本 3540100 存档在 `tools/sqlite3/`。

## 9. 代理与网络（M1-1 后半发现）

### 坑 26：本机有常驻代理（Clash Verge 127.0.0.1:7897），之前"GitHub 全被墙"的结论要修正

- 现象：之前认定 GitHub 直连不通（坑 12/22），实际本机 7897 端口有常驻代理，github.com / raw.githubusercontent / release CDN 经代理全部 200。
- 解法（已固化）：`scripts/dev-shell.sh` 启动时探测 7897 存活则导出 `HTTP(S)_PROXY`，国内镜像域名进 `NO_PROXY` 不走代理。**新 shell 一律先 source dev-shell.sh**，下载类操作自动获得代理。
- 解锁清单：cargo-deny 预编译二进制（GitHub Releases，sha256 校验后解压 `tools/cargo-deny-bin/`）；Tauri 打包器拉 NSIS；RustSec advisory DB；理论上 openWakeWord 模型、现代 mingw gcc 也可走代理解决——**坑 25b 的"拿不到现代 mingw gcc"在代理下可能不再是死路**。
- 注意：代理是用户机器上的 Clash，重启/关闭后 7897 会消失，dev-shell.sh 会自动回退直连（国内镜像不受影响）。

### 坑 27：打包链路的三个连环坑（M1-1.6）

- **坑 27a：npm 版 tauri CLI 在本机不可用**。`npx tauri` / `node_modules/.bin/tauri.cmd` 都报 `unrecognized subcommand '...\Kimi.exe'`——@tauri-apps/cli 的 NAPI 原生 addon 在 Kimi 托管的 node v24 下 argv 解析错乱。**解法：弃用 npm 版，改用 Rust 原生 `cargo install tauri-cli`（2.12.4，约 15 分钟分 chunk 编完，无 C 依赖不触发坑 25b），命令为 `cargo tauri build`。**
- **坑 27b：tauri v2 配置键名以官方 `config.schema.json` 为准**（在 cargo registry 的 tauri-cli 目录里），文档/旧教程常对不上。实测：`bundle.windows.webviewInstallMode` = `{"type":"downloadBootstrapper","silent":true}`（**type 小写**）；`bundle.windows.nsis.installerHooks` 是**字符串**不是数组，路径相对 tauri.conf 所在目录；钩子宏名是 `!macro NSIS_HOOK_POSTINSTALL`（不是 v1 的 customInstall）。
- **坑 27c：动态链接 DLL（sqlite3.dll）不能走 tauri resources**。resources 落在安装目录 `resources/` 子目录，而 Windows 加载器只搜 exe 同级目录——进程启动即弹"找不到 sqlite3.dll"（import lib 是加载期绑定，main 里再拷来不及）。**解法：NSIS 安装钩子** `NSIS_HOOK_POSTINSTALL` 把 resources\sqlite3.dll 拷到安装根 + `NSIS_HOOK_PREUNINSTALL` 删除（installer-hooks.nsh，已入库）。dev 模式不受影响（build.rs 已拷到 target/debug）。

## 10. 系统层事件采集（M1-2）

### 坑 28：windows-sys 的 WINEVENTPROC 签名与真 ABI 不一致（少 dwContext 参数）

`SetWinEventHook` 的真 ABI 会把安装时传入的 `dwContext` 作为**第 8 个参数**塞进回调，但 windows-sys 0.61 的 `WINEVENTPROC` 类型只有 7 参（文档签名的样子）——`Some(callback)` 直接传 8 参函数编译不过，也拿不到 context 指针。**解法：进程内单例 `static CTX: OnceLock<Ctx>` 替代传参**（全局只有一个采集器实例，语义恰好吻合）；x64 下按 7 参编译的回调收到 8 个实参是安全的（多出实参被忽略）。

### 坑 29：GetLastInputInfo / LASTINPUTINFO 的 import 归属反直觉

它不在 `Win32::UI::WindowsAndMessaging`（winuser.h 的大多数函数在那），而在 `Win32::UI::Input::KeyboardAndMouse`。Cargo.toml 的 feature 注释若只写 WindowsAndMessaging 会 import 失败。

### 坑 30：cargo build 报"拒绝访问 (os error 5)"先查进程锁，不是权限问题

目标 exe 正在运行（含后台残留进程）时，链接器写不进 `target/debug/chaojiandai.exe` 就报这个。**解法：`Stop-Process -Name chaojiandai -Force` 再构建**。自动化脚本里顺序必须是 杀 → 编 → 启。

### 坑 31：PowerShell Add-Type 内联 C# 经 Git Bash heredoc 传参会乱码编译失败

含中文/转义引号的 C# 源码穿过 bash → powershell -Command → Add-Type 三层编码后必出"乱码错误"。**解法：调 Win32 小函数直接用 Python ctypes**（内部托管 Python 自带，无编码问题），别在 shell 里拼 C#。

### 坑 32：前端改动必须「npm build → 强制 cargo build」才进 exe，WebView2 缓存+残留进程会联手骗人（M1-2 调试阶段连环坑）

Tauri v2 的 `frontendDist` 在**编译 exe 时嵌入二进制**；只跑 `npm run build` 不重新链接，运行的一直是旧页面。三个连环表象：
1. 改 dist 重启后页面没变 → 以为是 WebView2 磁盘缓存（`%LOCALAPPDATA%/<identifier>/EBWebView`），删了也没用；
2. 真凶之二：`Stop-Process` 只杀主 exe，**`msedgewebview2.exe` 子进程常驻**（按 CommandLine 含 app 名过滤可找到 6 个），新 exe 会复用旧浏览器进程组，内存里还是旧页面；
3. 真凶之三：即使源文件没变，cargo 不会重链接，`generate_context!` 不会重新嵌入新 dist。

**解法（标准重启流程）**：杀 chaojiandai + 杀 CommandLine 含 chaojiandai 的 msedgewebview2.exe → `npm run build` → `cargo clean -p chaojiandai && cargo build`（或 touch src/main.rs）→ 启动。诊断口诀：**「页面没变先怀疑嵌入了旧 dist，别怀疑 WebView2 缓存」**。

### 坑 33：windows-sys 0.61 是「模块级 + 条目级」双层 feature 门控，错误提示会骗人（M1-2 网络采集）

`Win32_NetworkManagement_IpHelper` 只开门（模块可见），模块内**每个函数/结构再按项 cfg**：`GetAdaptersAddresses` 要 `Win32_NetworkManagement_Ndis` + `Win32_Networking_WinSock`，`NotifyAddrChange` 要 `Win32_System_IO`，`IP_ADAPTER_ADDRESSES_LH` 也要 Ndis/WinSock。报错只说「no X in module」，不告诉你缺哪个 feature——**看编译器的 `found an item that was configured out` 注记，点进注记给的源码行看那一行的 `#[cfg(...)]`**。另：`IP_ADAPTER_ADDRESSES` 是纯类型别名，实际结构体名是 `IP_ADAPTER_ADDRESSES_LH`；`OperStatus` 是 NDIS 的 `IF_OPER_STATUS`（i32 常量如 `IfOperStatusUp`）；`WaitForSingleObject` 在 `Win32::System::Threading` 不在 Foundation。

### 坑 34：windows-future 0.3 移除了阻塞式 get()，且 WinRT 异步是「双层 Result」（M1-2 SMTC）

- `IAsyncOperation<T>` 在 windows-future 0.2 有 `.get()` 阻塞等待，**0.3 删了**，只剩 std feature 的 `IntoFuture`——阻塞等待要自己写 block_on（park/unpark + Wake，20 行内）；
- 等待结果是**双层 Result**：`RequestAsync()?` 拆出 `IAsyncOperation<T>`，`IntoFuture::Output` 本身还是 `Result<T>`——`block_on(op)?` 才是 `T`，写成 `??` 或单层都是错；
- 本地 registry 里可能留着旧版本源码（如 windows-future-0.2.0），**查 API 前先确认 Cargo.lock 里的实际版本**，别照着旧源码写。

## 11. 语音管线（M1-3）

### 坑 35：sherpa-onnx 本机落地的正确姿势与两个 API 错觉（M1-3.1 spike）

- **预编译包直接可用**（比 sqlite 顺利）：GitHub Release 的 `win-x64-shared-MD-MinSizeRel.tar.bz2`（18.9MB，含 onnxruntime 14MB）自带 MSVC 导入库，rust-lld（gnu-lld flavor）可直接消费，无需 dlltool；DLL 三个都要随 exe（sherpa-onnx-c-api / onnxruntime / onnxruntime_providers_shared），build.rs 照 sqlite 模式拷 target/<profile>/ 与 deps/。
- **错觉一**：`SherpaOnnxGetKeywordResult` **总是返回结果对象**——没命中时 `keyword` 是空串不是 NULL；判命中要查空串。
- **错觉二**：示例里的 `RequestAsync().get()`——`.get()` 只存在于旧版绑定，C API 是同步函数，Rust 侧用 FFI 直调无此问题（windows crate 那边的 get 坑见坑 34）。
- FFI 结构体逐字段抄自 `c-api.h` v2.0.1，**升级版本必须复核 repr(C) 布局**（v2.0.1 已把 v1.x 的 KeywordSpotterAcceptWaveform 合并进通用 OnlineStreamAcceptWaveform）。

### 坑 36：语音链路"无人在场"端到端验证 + 两个日志盲区（M1-3.3）

- **扬声器→麦克风回路自测**：不用真人喊——`powershell -NoProfile -Command "$p = New-Object System.Media.SoundPlayer '<wav 绝对路径>'; $p.PlaySync()"` 播放 M0 录音，麦克风阵列收音，KWS/VAD 全链路走真实音频路径。KWS 用 0.2s 块、引擎用 0.1s 块都能稳定命中。
- **日志盲区一**：tracing 没初始化时 `tracing_subscriber::fmt().init()` 之前所有 info!/error! 全丢（桌面 exe 无控制台）。已修：main.rs 落盘 `%TEMP%\chaojiandai-rust.log`。
- **日志盲区二**：`chaojiandai-events.log` **无时间戳且跨进程累积**——看到一条事件先确认是不是本次进程发的（对 `%TEMP%\chaojiandai-rust.log` 里的进程启动时间）。
- VAD 输入必须 512 对齐（silero window_size），引擎侧用独立 vad_buf 攒 2048 再喂；0.1s 块（1600）直接喂会踩 debug_assert。

### 坑 37：Senary 麦克风阵列"信号增强"（DSP）会间歇性把语音门控成数字静音（2026-11-12 坐实）

- **症状**：同一套代码好坏交替——有时 VAD 4/4 全中，有时监听窗口 rms 精确为 0.00000（物理麦克风不可能输出全零）、转写音量只有正常 1/6。白天四连漏、傍晚四连中，无代码差异。
- **根因**：Windows 输入设备默认开启"音频增强/信号增强"（MMDevices 里 `Disable_SysFx` 未设置 = 开启），Senary 的降噪/波束成形 DSP 会整段吞掉它判定的"非目标"语音。排查脚本：`scripts/check-mic-fx.ps1`（读各录音设备的增强开关状态；`fx_disabled=not-set` 即开启）。
- **解法**：设置 → 系统 → 声音 → 输入 → 麦克风阵列 (Senary Audio) → 关闭「音频增强」。改完需**重启应用**（采集流在启动时建立）。
- **副作用**：关掉后麦克风灵敏度大幅上升——附近的视频人声会被 VAD 当指令收进来（实测收到 6 秒背景视频转写）。后续靠 VAD 阈值/最小语音时长/唤醒后才开听来收敛，不要再把增强开回去（门控比噪声更毒）。
- **推论**：发给最终用户的安装手册里应写明"关闭输入设备音频增强"，或引擎启动时检测并提示。

### 坑 38：`cargo test` 全绿 ≠ exe 是新的——测试二进制与主程序二进制是两份产物（M1-3.5a 实机验证）

- **症状**：改完 Rust 跑 `cargo test` 16 项全绿，启动 `target/debug/chaojiandai.exe` 实机验证——跑的却是旧代码，新加的日志一行没有，现象"代码像没生效"。
- **根因**：`cargo test` 编译的是 **test harness 版** bin（`chaojiandai-<hash>.exe`），不会刷新 `target/debug/chaojiandai.exe`。CI 过了、测试过了，主程序照样是几小时前的旧产物。
- **排查姿势**：启动前先对比时间戳 `ls -l --time-style=full-iso target/debug/chaojiandai.exe` vs 最新源码 mtime；或启动后直接 grep 日志里新代码必打的行（本次靠 `llm sidecar: spawning` 定位）。
- **解法**：重启验证前**必须显式 `cargo build`**（不是 `cargo test`，也不是只跑 CI 脚本里的 lint 项）；dev-shell 的提示语已写「构建: cd src-tauri && cargo build」，照做。
- **顺手教训**：单测断言里的算术要自己数一遍——本次 `system + 2 轮×2 + 当前 = 7` 实为 6，实现是对的、测试期望值写错了，白排查一轮。
